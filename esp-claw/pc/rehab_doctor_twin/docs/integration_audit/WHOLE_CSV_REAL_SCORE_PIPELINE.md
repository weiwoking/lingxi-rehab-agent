# Whole CSV Real Score Pipeline

## Whole CSV as the job input

The formal Score Job input is one complete raw 86-column training CSV plus the frozen seven-field `task.json` contract. The PC doctor backend and verification script must not split, trim, resample, smooth, fill, or rewrite the CSV before submitting it.

Using the whole CSV does not mean treating the entire 47-second sequence as one drink action. The CSV is a whole training session. The score service loads it once, validates it once, then performs action-cycle segmentation inside the service.

## Session ID is the formal source of truth

The formal system must not hard-code `TASK006` or any other fixed session as a production data source. `TASK006` is only a repair-verification sample.

Every formal run is indexed by the current `session_id`:

```text
runtime_data\sessions\<session_id>\
  task.json
  DATA_SEQ*.csv
  job_status.json
  result\
    score_result.json
    trajectories\
```

For each new `TASK` session directory, the complete CSV is written into that same directory, the score service reads that same complete CSV directly, and the service writes `result\score_result.json` plus `result\trajectories\` under that same `session_id`. The doctor log, report pages, and waveform replay all resolve files by `session_id`; no production path copies the session into another formal directory or depends on `20260726_TASK006`.

When the doctor backend adopts an already complete session for automatic scoring, it submits the original `task.json` bytes from this directory. It may parse the bytes to validate the frozen seven-field contract, but it must not regenerate JSON for identity comparison, because whitespace, indentation, newline style, or field order would change the task SHA-256.

## Internal action-cycle processing

The current score service path is:

1. `ScoreJobStore.receive_csv()` validates the uploaded CSV header, size, SHA-256, and first/last `log_seq`.
2. `ScoreJobWorker.process_one()` verifies persisted task/CSV identity and calls the scorer with the validated session directory.
3. `process_task_directory()` reads `task.json`, loads the task-declared CSV with `read_fused_csv()`, and validates manifest `log_seq`.
4. `process_session_dataframe()` chooses the drink full-cycle route when `task_name` is the drink task and `REHAB_SCORE_DRINK_FULL_CYCLE=1`.
5. `segment_drink_complete_cycles()` identifies complete drink cycles inside the whole CSV.
6. Each detected segment is converted to a trial through `build_trial_from_segment()` and scored by the existing `score_trial_full_json()` / DTW / EMG scoring calls.
7. `summarize_session()` aggregates valid action scores into the session-level `summary.average_score`.
8. `process_session_dataframe()` writes `result/score_result.json`.

No scoring formula, score weight, threshold, or standard trajectory is changed by this fix.

## trajectories directory

`trajectories/` is an internal score-service artifact directory under the job output directory. In the Job API path that location is:

`runtime_data/sessions/<session_id>/result/trajectories/`

For successful detected actions, `save_action_trajectory_artifacts()` writes per-action trajectory JSON/PNG files there. For zero detected actions, the directory still exists so the worker can distinguish a legal `valid=false` business result from a broken scorer.

The directory is not an input contract. It is not generated by the frontend, doctor backend, P4/S3, or user scripts.

## TASK006 verification sample

TASK006 already passed input validation and is useful as a fixed repair-verification sample. It is not the formal data source for the running product. Its failure message, `scorer did not create the trajectories directory`, is consistent with the scorer finishing without creating any per-action trajectory artifact directory, after which the worker treated the missing intermediate directory as a program failure.

This round fixes the service output structure so `result/trajectories/` exists even when no complete valid action cycle is detected. In that case `score_result.json` is still written with `valid=false`, `final_score`/`summary.average_score=null`, `actions=[]`, and feedback explaining that no complete valid action cycle was detected.

## Multiple actions and total score

When multiple complete cycles are detected, each action continues to use the existing action scoring path. The session total remains the existing aggregation rule in `summarize_session()`, not the first action score and not a DTW over the whole session.

## Verification method

The user can run `scripts/verify_real_score_from_task006.ps1` manually after starting the score service. The script creates a new Job ID, submits the complete original TASK006 CSV once through the formal Job API, polls status, and prints compact and full-result summary fields. This verifies the repaired whole-CSV scorer path only; it does not make TASK006 a production source.

The script does not modify TASK006 and does not directly call internal Python scoring functions.

## Report and log chain

When a new real Job succeeds, the doctor backend reads the full `result/score_result.json`, stores its own session result references, builds `report.json`, and exposes the same real result to doctor reports, patient reports, overview score, and prediction when existing eligibility conditions are satisfied.

When scoring fails, the training fact still remains in the doctor data log with score failed and report not generated.

## CSV replay separation

Patient CSV replay reads the same original CSV only for waveform display. It does not create sessions, write CSV, score, enter prediction, or feed the scoring path. Scoring input is always the original complete CSV submitted to the score service.

## Automatic session discovery

The formal product path is not `TASK006` and is not `PC_STREAM_CSV_PATH`. The doctor backend watches `runtime_data\sessions\<session_id>`, validates each `session_id`, reads the CSV declared by that session's `task.json`, and keeps scoring output under the same `session_id`.

Waveform playback and scoring both read the same original CSV, but they are independent read-only paths. Replay never triggers scoring; score completion is observed through `job_status.json` and `result\score_result.json`.

Playback mode remains tied to session completeness: unfinished task manifests use tail mode, finalized task manifests use replay mode, and later score-state changes only update log/report status.
